# 河流水质站日 CSV 发布服务

面向科研核验的不可改原件发布 API：原件原字节存共享卷，SQLite 只存目录与摘要，
以 SHA-256 固定深度 Merkle 树出具检查点、单件纳入证明与检查点追加证明，
并提供完全离线的验证函数/CLI。两个实例挂载同一卷并发发布，不分叉、不覆盖。
支持在发满初始 128 件后做**一次性扩容到 256 件**：扩容不占发布序号、不改旧根，
旧证明持续有效，并提供跨扩容的追加证明以离线确认历史连续。

## 1. 目录结构

```
app/
  config.py     运行配置（DATA_DIR、1 MiB、初始 128 件、树深度 7）
  storage.py    原件字节存储：内容寻址 + 临时文件 fsync + 原子改名
  db.py         SQLite 持久层：WAL、BEGIN IMMEDIATE 串行化、容量 meta、启动自检
  merkle.py     Merkle 树纯函数：根、纳入证明、追加证明（含跨深度）、离线验证
  verify.py     离线核验函数与 CLI（python -m app.verify ...）
  schemas.py    HTTP 响应模型
  main.py       FastAPI 路由（阻塞调用均走线程池）
tests/          29 项 pytest 用例（算法、API、扩容、故障路径）
scripts/
  demo.sh                 HTTP 端到端演示
  dual_instance_check.py  双进程共卷并发/扩容/故障转移集成检查
Dockerfile
docker-compose.yml        两个实例共卷，端口 8001/8002
```

## 2. 启动

### Docker Compose（交付目标形态）

```bash
docker compose up --build
# 实例 A：http://localhost:8001/docs
# 实例 B：http://localhost:8002/docs
```

两实例镜像相同、挂载同一命名卷 `shared-data`（`/data`），
`MAX_FILE_BYTES=1048576`、`MAX_RELEASES=128`（全新卷初始 Merkle 深度 7，
128 个叶子槽位；发满后经 `POST /capacity/expand` 一次性扩容到 256、深度 8）。

### 本地直接运行

```bash
python -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt
DATA_DIR=./data uvicorn app.main:app --port 8000
# 打开 http://localhost:8000/docs
```

## 3. API 一览（/docs 可交互演示）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/releases` | 表单 `station_id`、`sample_date`(YYYY-MM-DD)、`order_no`、`file`；同单同输入重试复用（`reused=true`），异输入 409，超 1 MiB 返回 413，超 128 件返回 409，写盘失败返回 507 |
| GET | `/releases` | 全部发布目录记录（不含字节） |
| GET | `/releases/{station}/{date}/{order}` | 单条目录记录 |
| GET | `/releases/{station}/{date}/{order}/download` | 下载已提交原件，文件名带站日单号 |
| GET | `/releases/{station}/{date}/{order}/inclusion-proof` | 单件纳入证明（恒 7 步路径） |
| GET | `/checkpoints` | 全部检查点（含 0 号空树检查点） |
| GET | `/checkpoints/latest` | 最新检查点（条数 + Merkle 根） |
| GET | `/checkpoints/{seq}` | 任意旧检查点 |
| GET | `/checkpoints/{old_seq}/append-proof` | 旧检查点 → 最新检查点的追加证明（支持跨扩容，带 `old_tree_depth`/`tree_depth` 双深度） |
| GET | `/capacity` | 当前容量、树深度、已发布条数、是否已扩容、剩余槽位 |
| POST | `/capacity/expand` | 一次性扩容：仅在发满当前容量时把上限 128→256（深度 7→8）；未满或已扩过返回 409，两实例并发只生效一次，失败不改动状态、可重试 |
| GET | `/health` | 启动自检结果（缺件/摘要不符/深度异常时 `degraded`，并拒发证明与下载） |

## 4. 核验模型（科研组离线使用）

### 叶子与树

* 叶子载荷为带版本号的规范化 JSON（键排序、无空白）：
  `{v, station_id, sample_date, order_no, blob_sha256, size}`，
  叶子哈希 = `SHA256(0x00 || 载荷)`；内部节点 = `SHA256(0x01 || left || right)`，域分隔防二阶碰撞。
* 固定深度 7 的完整二叉树，未用槽位以公开常量 `EMPTY_LEAF` 占位：
  追加只改变新叶子到根的路径，旧证明不会因树“长高”失效。
* **纳入证明**：7 个兄弟哈希（O(log n)），每步带 `bit` 与下标逐位绑定，防重放到其他下标。
* **追加证明**：把旧前缀与新增区间分别平铺为对齐的完美子树，条目数 ≤ 2×深度（实测 128 件规模最多 8 条）。

### 一次性扩容（128 → 256）的树模型

容量即固定深度树的叶子槽位数。扩容把树深度由 7 升到 8（槽位 128 → 256），
采用**按检查点绑定深度（epoch）**的方案，保证旧证明与旧根不受影响：

* **旧检查点不改写**：扩容前的每个检查点保留其生成时的深度（7）与根摘要，
  扩容动作只更新 `meta` 容量，不写检查点、不占发布序号；旧纳入证明 JSON 自带
  `tree_depth=7`，离线端按其自带深度核验，扩容后仍然有效。
* **新检查点用深度 8**：扩容后续发的第 129 件起，新检查点按深度 8 计算根，
  旧叶子位于新树左半子树，叶子下标与规范化载荷不变。
* **跨扩容追加证明**：证明条目按新树（深度 8）平铺为对齐完美子树，同一份条目
  分别在深度 7（重建旧根）与深度 8（重建新根）下复算，离线即可确认扩容前后
  历史连续；条目数仍 ≤ 2×新深度，随条数对数增长。
* 容量状态（当前容量、初始容量、硬性上限=初始×2）持久化在共享卷 `meta` 表，
  重启后以卷为准，环境变量不覆盖已扩容的卷；硬性上限保证扩容严格一次性。

### 离线核验（无需服务端、无需网络）

```bash
# 单件：凭留存的纳入证明 + 待验原件，核验站日归属与检查点纳入
python -m app.verify inclusion --proof inclusion.json --file 原件.csv

# 历史前缀：凭两个留存检查点 + 追加证明，核验仅追加关系
python -m app.verify append --proof append.json \
  --old-checkpoint cp-old.json --new-checkpoint cp-new.json
```

也可直接导入纯函数：`app.verify.verify_release_bytes`、`app.verify.verify_append_proof`。
篡改原件、替换历史条目、伪造检查点根、证明重放到其他下标均会被拒绝（退出码 1）。

## 5. 崩溃安全与并发不变量

1. **先落盘后入库**：原件写临时文件 → `fsync` → `os.replace` 原子改名 → `fsync` 目录，
   成功后才开数据库事务；写盘失败无库记录、临时文件清理、可原样重试。
2. **串行化发布**：每个发布事务 `BEGIN IMMEDIATE`，双实例写操作被 SQLite 锁串行化，
   后到者等待后重检唯一键 `(station_id, sample_date, order_no)`；无 UPDATE/DELETE 路径。
3. **只增不改**：同键同字节复用、同键异字节 409；检查点与记录均只追加。
4. **启动自检**：重算全部叶子与根，逐件校验卷上原件摘要并检查序号稠密、检查点连续；
   发现缺件即 `degraded`，拒绝发布/证明/下载，绝不输出缺件记录。
5. **重启有效**：历史检查点根由固定深度树确定，重启后逐点按其自身深度复算一致，
   容量状态从共享卷 `meta` 恢复，留存证明持续有效。
6. 阻塞式磁盘/DB 调用均在任意线程池执行，锁等待不阻塞事件循环；
   写锁冲突在 `busy_timeout` 之外另有 3 次有限重试。
7. **扩容串行化**：`POST /capacity/expand` 与发布同在 `BEGIN IMMEDIATE` 事务内，
   两实例并发请求被 SQLite 锁串行化，恰有一次真正翻倍；未满当前容量或已达硬性
   上限（初始容量×2）时返回 409 且不改任何状态，可原样重试。

## 6. 测试结果（本环境实测）

* `pytest tests/`：**29 项全部通过**
  - Merkle：根稳定性、纳入证明、全部前缀追加证明、篡改/重放/重叠/缺口拒绝、
    平铺覆盖性质、跨深度（7→8）追加证明与满 256 槽边界；
  - API：发布、幂等复用、409 冲突、413/422 限额与校验、上限拒绝、下载字节一致、
    两类证明与离线核验、容量状态与扩容端点；
  - 扩容（`tests/test_expansion.py`，7 项）：未满拒绝、发满→扩容→续发、一次性、
    并发交错只生效一次、失败回滚可重试、跨扩容离线核验、重启后容量恢复与自检；
  - 故障：写盘失败不留记录且可重试、缺件自检与 503 拒服、孤立临时/原件无害、
    已引用原件被改可检出、重启后检查点按各自深度可复算。
* `scripts/dual_instance_check.py`（两个独立 uvicorn 进程共卷，初始容量 8）：
  **28 项全部通过**，覆盖并发同单（一写一复用）、并发异单序号稠密、跨实例取件/
  检查点/证明、**发满后两实例并发扩容恰一次生效（200+409）、扩容不占序号、
  第 9 件续发、跨扩容追加证明离线核验、旧纳入证明扩容后仍有效、第三进程挂同卷
  故障转移后容量/历史完整且扩容仍不可重复**。
* 手工冒烟（小容量卷 4→8）：未满扩容 409、发满后第 5 件 409、扩容成功且重复
  扩容 409、扩容不写检查点、续发第 5–8 件、第 9 件触硬上限 409、旧检查点根摘要
  扩容前后逐字节一致、CLI 离线核验全通过、篡改旧根被拒；重启后容量以卷为准。
* 旧库迁移实测：对不含 `tree_depth` 列与容量 `meta` 的旧版 SQLite 启动新代码，
  自动补列（旧检查点深度置 7）并写入容量元数据，历史根摘要不变。
* 证明规模实测：纳入证明长度恒等于树深度（扩容前 7 步、扩容后 8 步）；
  跨扩容追加证明条目数 ≤ 2×新深度（深度 7→8 规模上界 16，实测常见 2–8 条）。

## 7. 剩余工作与已知限制（据实说明）

1. **本环境无 Docker 守护进程**，`docker compose` 未实际起容器验证；已用双 uvicorn
   进程共享同一 `DATA_DIR` 做等价并发/故障转移测试。Dockerfile 与 compose 配置已交付，
   需在具备 Docker 的环境执行一次 `docker compose up --build` 复核。
2. 沙箱以 seccomp 禁止 `kill` 系统调用，集成脚本无法终止演示进程，改为随机端口 +
   每次独立临时目录；脚本中的“重启”以第三进程挂同卷模拟（故障转移语义等价）。
3. 容量上限在实现上是固定深度树的叶子槽位数（2 的幂，可经 `MAX_RELEASES` 调整
   全新卷的初始值）；扩容严格一次性，最多把初始容量翻倍（默认 128→256），
   不支持继续扩到 512。非 2 的幂配置会在启动时直接报错。
4. 未引入鉴权/传输加密/TLS，定位为内网或网关后的发布服务；对外暴露需前置网关。
5. 共享卷自身的备份与异地容灾未包含在本服务内（卷快照/备份应由基础设施层提供）；
   服务能检出卷上缺件与篡改，但不会自动恢复字节。
6. 原件类型未强制 CSV 内容嗅探，仅做大小与空文件校验，避免对业务 CSV 方言做过强假设。
